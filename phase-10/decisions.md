# Phase 10 decisions

## P10-D91 — Remove fallback/repair scripts (2026-11-18 UTC)

The user explicitly requested removing the scripts added to handle RabbitMQ fallback/missed messages. Remove P10-32's maintenance CLI, dry-run/apply/bootstrap flow, shared maintenance-only helper, Identity snapshot endpoint and its supporting types/queries, dedicated tests and runbooks. Restore the original Identity lifecycle consumer implementation. The existing outbox/inbox, normal RabbitMQ retry behavior and previously existing tools are unchanged.

This supersedes the maintenance/bootstrap portion of P10-D90 and the original plan. Keep the create/activate tenant linking fixes, room address/contact/photo responses, favorite API/migration and their regression tests. No new replay, fallback or historical-data repair script is required for this work.

## P10-D90 — Mobile backend fixes and tenant favorite rooms (2026-11-18 UTC)

The user approved implementing the audited mobile-backend plan (P10-31–37 and existing P10-24). This supersedes the favorite-room implementation deferral for the backend/API slice only. It does not approve a tenant picker, payment work, unrelated roommate features, or claim deployment/mobile acceptance. See [implementation evidence](discovery/mobile-backend-implementation.md).

Contract creation resolves an absent tenantId from the local active-tenant Identity phone projection; activation retries for NULL drafts before representative creation and activation context. Exact normalized phone matching, explicit-ID precedence, local transactions/outbox and Identity lifecycle inbox remain in force. Existing NULL contract/member links may be repaired with an explicit dry-run/apply maintenance command. Historical links must not be transferred. Because account snapshots and Tenancy writes cannot be atomic across services, applying a bootstrap snapshot requires temporarily pausing Identity account mutations and draining lifecycle events; the command documents and requires that operator assertion rather than silently assuming a snapshot is current.

Tenancy owns favorites keyed by authenticated tenant user ID and room ID, with a unique composite key. No additional tenant profile is required. GET returns an empty paginated 200 for no eligible favorites. Only available rooms in approved, undeleted buildings may be added/listed. Hidden, occupied or deleted rooms are omitted from the list while their saved links remain removable; becoming eligible again restores list visibility. POST of an existing eligible favorite returns 409 ALREADY_FAVORITED; DELETE removes only the caller's row, returns 204, and returns 404 RESOURCE_NOT_FOUND when absent. Public room search returns viewer-specific isFavorited only with a verified token and varies caching by Authorization.

Room list/detail return building address fields directly. Detail resolves the owner's id/name/phone from Identity and never forwards email. A missing/deleted/non-landlord owner makes detail unavailable (404); Identity outage remains 503 rather than successful null contact. photoUrls is the primary display contract; nullable deprecated thumbnailUrl remains as a compatibility alias on lists. Display URLs must belong to uploaded room cover/gallery media; metadata endpoints are not image fallbacks. Favorite/public-room lists support JSON only until an export feature is implemented.

Acceptance still requires review/deployment, migration, actual-account repair, real photo upload and the correct Android source/build. Local PostgreSQL WASM tests verify SQL/rollback, not independent connection races, RabbitMQ delivery or the user's actual mobile screen.

## P10-D89 — Tenant match requests and notifications (2026-11-16 UTC)

The user approved P10-26 with notifications. Tenancy Service owns direct tenant-to-tenant match requests; this approval supersedes the P10-D88 deferral for P10-26 only. P10-27 Web UI, AI scoring/advice, matched-roommate chat, and contact-detail disclosure remain deferred. Account-holding active tenants may send requests to another active tenant whose roommate profile is currently discoverable under P10-D88. No landlord approval is part of this flow, and passive tenants are not required to create accounts.

Only the recipient may accept or reject a pending request; only the requester may withdraw it. A repeat of the same completed action returns the current request without another event; a different action after the request leaves pending returns `MATCH_REQUEST_NOT_PENDING`. At most one pending request is allowed for an unordered tenant pair. After rejection or withdrawal, a new request is allowed. `POST /match-requests` requires a UUID `Idempotency-Key` scoped to the requester: replay with the same target returns the existing request and creates no notification, including when that request has since changed status; reuse with a different target returns `IDEMPOTENCY_KEY_REUSED`. A different key while a pair is pending returns `DUPLICATE_MATCH_REQUEST`. Request creation and transitions persist their state and a match request domain event (`match_request.created`, `match_request.accepted`, `match_request.rejected`, or `match_request.withdrawn`) in the outbox in one transaction. The event identifies its recipient in Tenancy: the target on creation and withdrawal, the requester on acceptance and rejection. Community's existing inbox deduplicates replayed events and delivers its normal in-app, socket, and push notification. Request lists expose only the caller's incoming/outgoing requests and do not expose phone, AI fields, or conversation IDs.

An existing pending request remains actionable if the target profile later becomes hidden or the room becomes full; the acting account must still be active. P1-13 remains a design reference only where it does not conflict with P10-D88/P10-D89. Update the OpenAPI draft to match this contract before marking operations released.

## P10-D88 — Basic roommate profiles in Phase 10 (2026-11-16 UTC)

The user approved P10-25 for Phase 10. This slice covers account-holding tenants saving their own roommate profile and browsing basic profiles. Match requests (P10-26), AI scores/advice, and Web UI (P10-27) remain deferred. This narrows the older D28 Stretch classification for profile CRUD/search only; it does not approve the rest of matching.

Tenancy Service owns profile persistence and the four public API operations. Identity remains the source of the user's name, public avatar, role and account status, read through the existing internal HTTP lookup. Public profile responses expose only approved fields; they never forward Identity email/phone or contract/member data. Only active tenant accounts may save, list or view profiles. A tenant may read their own profile even while it is hidden. Other tenants can read a profile only while it qualifies for search; an ineligible profile returns 404 on direct detail lookup as well as being omitted from lists.

`isVisible` is the tenant's persisted opt-in and is never changed automatically. An active contract does not by itself hide the profile, superseding the auto-hide rule in P1-13 for this slice. Search eligibility also requires a vacancy in at least one room of the tenant's active contracts. For a tenant with no active contract, `isVisible` suffices. A room with `maxOccupancy = null` has no configured capacity limit. Occupancy counts the contract's lead tenant plus distinct current members, including members without an account; apply effective join/leave dates and avoid double-counting the lead. A full room temporarily excludes the profile from search without modifying `isVisible`; eligibility is recalculated as contract, membership or room capacity changes. When several active contracts exist, one room with a vacancy is sufficient. Direct detail and paginated search use the same eligibility rule.

The basic profile has `isVisible`, a nonempty `bio` when visible, optional `gender`, `birthYear`, `occupation`, preferred province/district/area, budget bounds, move-in date, and human-readable lifestyle flags. If both budget bounds are provided, minimum must not exceed maximum. `GET /me/roommate-profile` returns all saved fields; name/avatar are read from Identity for public views. Do not add `isDiscoverable` or `visibilityReason`. Remove AI scores/advice and unused `personality`/identity-verification fields from this slice's API contract. The endpoint remains `designing` until implementation and verification.

This is a Phase 10 scope boundary, not a decision to discard future matching or AI work. P1-13 remains the design reference for that later work except where P10-D88 explicitly supersedes it. A future AI score or advice result needs a separately approved contract because it can depend on the viewer, candidate and matching context; it should not be treated as a permanent attribute of the basic roommate profile. Future profile inputs such as `personality` may be added through an approved additive API and storage change without requiring existing basic profiles to contain them.

The existing `api-doc` draft stays unchanged while P10-25 is pending. Align its OpenAPI contract after the basic profile feature is complete and verified.

## P10-D87 — Tenant room hub (2026-11-15 UTC)

The user requested P10-14 and delegated the design. The endpoint returns a paginated list with one item per active contract, including room and building identifiers, names, address, room area, contract dates and contract rent. No matching contract returns an empty list. Multiple contracts are returned in descending start-date order with contract ID as a tie-breaker. The named tenant and currently linked members have the same access as `/me/contracts`; soft-deleted contracts, rooms and buildings are excluded. Payment, invoice payment state, issue counts and contact details are not inferred. This decision enables the API independently of the P10-15 lite web flow, which continues to use its existing endpoints. The response replaces the old unimplemented draft schema.

## P10-D86 — Issue reports and notifications (2026-11-14 UTC)

The user approved implementing P10-28 and P10-29 with Community Service owning issue reports. Each issue is associated with a room and its active contract at creation. The room's landlord and current contract tenants can create and view issues. A landlord can create a report for a tenant who does not use the application. Tenants lose access after leaving; other landlords and tenants outside the contract cannot access the report or its images. Authorization is enforced by the backend on every request.

The landlord can move an issue from `open` to `in_progress` and then `resolved`. Its creator can cancel it before resolution. Resolved and cancelled issues are terminal. Concurrent actions must preserve these transitions.

Images and notifications are in scope. Images use the existing private Media service and a real IssueReport ownership resolver. Since Media requires an existing owner, create the issue before uploading its images. Only completed images attached to that issue may be shown. Notifications use English event keys and data in the backend payload, translated by the frontend. Notification recipients must be authorized for the issue, with retry-safe delivery. The `@issue` chat command and tagging are out of scope.

This decision supersedes the IssueReport deferral in P6-D61 and P9-D83 for this work; it does not change the scope of payment, deposit settlement, OCR, or other deferred features. OpenAPI and the implementation must describe the implemented contract consistently.
